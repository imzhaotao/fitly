## 1. 这个项目从哪来

起点是一个想法：做一个解决装修选品决策的工具。

最初考虑过**师傅入驻平台模式**，被彻底否掉，原因有三个（商业与履约本质，与开发周期无关）：

1. **师傅不缺活。** 好师傅排期都很满，没有动机入驻新平台。
2. **管不住。** 报价不透明、施工纠纷极难治理。
3. **水太深。** 硬装施工涉及水电改造、防水、燃气、承重拆改，风险远高于平台收益。

于是坚定转向**工具模式**：聚焦**软装与买家具/家电前**，让用户在**高质感 3D 空间**里摆进真实尺寸的家具、看净空与动线、做多方案对比并分享给家人一起拍板。

## 2. 关键认知与边界

### 原则一：以最优体验为标准，不做“将就的原型”

过去受限于单人手写代码时间，曾讨论过退回纯 2D 线框、砍成单空间、或用极简 URL 凑合分享。在 AI 协同开发模式下，**工程实现速度不再是瓶颈**，唯一重要的是**产品体验是否够惊艳、几何是否够准确、架构是否够扎实**：

- **必须做高质感 3D**：PBR 材质、柔和布光与接触阴影、高辨识度家具模型，同时内建**正交顶视图**和**人眼第一视角**，让屋主既能看清毫米级间距，也能真实感受“放进我家好不好看、压不压抑”。
- **覆盖核心三空间**：客厅、卧室、厨房一步到位，不做人为残缺版。
- **完整后端与协作**：用数据库承接云端快照、短链分享与家人投票表态，不再把复杂状态硬塞进超长 URL。

### 原则二：只管软装试装与布局避坑，不管硬装拆改施工

不砍工程质量，但**严守产品与法律安全边界**：

- **不涉及拆墙与承重结构**：拆墙、承重判断属于硬装结构工程，不在 Fitly 服务范围内。
- **水电、燃气、防水邻接只给提醒与提问清单**：当家具或大件家电邻接点位时，严禁输出施工参数（线径、空开、管径、防水遍数），只提醒隐患和“该问现场师傅/物业/燃气公司什么”。

### 原则三：从“空白户型起手”升级为“可编辑的设计模板起手 + 核心闭环”

“普通人自己画整套设计”是偏弱的首版假设；真实情况是**哪怕请了半包/全包师傅或设计师，绝大多数屋主仍要自己拍板家具尺寸与买前取舍**（甚至把改好的 3D 方案发给设计师或家人确认）。

因此，Fitly 不仅提供空白户型模板，更提供**同户型下不同功能取舍的可编辑设计模板**（例如 3.6 米客厅同时给“一家人观影型”和“给孩子留活动区型”两套好看且可改的方案）：用户先挑一套接近理想状态的布局，再改成自家开间与正在看的沙发尺寸，立刻看到净空与避坑变化。社区广场、广告电商暂不加入，以免稀释核心流程：**挑设计模板/建自家空间 → 3D 改尺试摆并触发避坑 → 对比并让家人/设计师一起定案**。

## 3. 已经定下来的决策（ADR 简表）

| 编号 | 决策 | 状态 | 理由 |
|---|---|---|---|
| D1 | 放弃师傅入驻 / 平台模式 | ✅ 采纳 | 供给侧没动机，履约风险不可控 |
| D2 | 从“纯看效果图”转向“可试摆、可量距、可避坑、可对比”的 3D 工具 | ✅ 采纳 | 既有空间美感，又有真实尺寸判断 |
| D3 | 先做 Web（移动与桌面响应式 Next.js 应用） | ✅ 采纳 | 免安装免审核、分享即开、同时兼容手机微调与电脑精绘户型 |
| D4 | **高质感轻量 3D（PBR 材质 + 软阴影）+ 顶视/平视切换** | ✅ 采纳（2026-11 升级） | 不为省时间做简陋方块；PBR 轻量模型兼顾加载速度与空间真实感 |
| D5 | 户型来源：**经典示例户型 + 参数化编辑 + 上传户型图辅助识别描墙校准** | ✅ 采纳（2026-11 升级） | 合规无版权风险，同时把建户型门槛降到最低 |
| D6 | 避坑内容做成**3D 几何联动触发器** | ✅ 采纳 | 与真实尺寸、高度、扫掠区联动，是核心护城河 |
| D7 | 英文名 / 仓库名 **Fitly** | ✅ 采纳 | npm 未被占用，短，可作 scope（`@fitly/*`） |
| D8 | 不做抓取外部平台户型库 | ✅ 采纳 | 有高额判赔先例（不正当竞争），且质量参差不齐 |
| D9 | 社区广场 / 家具电商 | ⏸ 推迟 | 先把单点决策与分享闭环打透 |
| D10 | 小程序 | ⏸ 推迟 | H5 分享闭环跑通后再评估是否用小程序承接微信入口 |
| D11 | 技术栈：**Next.js App Router + React Three Fiber + Drizzle ORM + 数据库** | ✅ 采纳（2026-11 升级） | 完整全栈能力：SSR 分享页、云端快照、短链与统计一体 |
| D12 | 不做“照片透视生成 3D 户型” | ✅ 采纳 | 普通照片缺少比例尺与正交信息，几何误差不可控 |
| D13 | **云端自动快照 + 版本列表 + 任意两版对比 + 分享页家人投票** | ✅ 采纳（2026-11 升级） | 解决“改之前长什么样”和“发给家人怎么一起定”的完整闭环 |
| D14 | 中文名：暂定「试家」备选（「装修匠」易误导为找师傅） | 🔶 待定 | 需查商标，详见 [06-naming.md](06-naming.md)；不阻塞开发 |
| D15 | 避坑内容：**检索规范做选题，严格守软装边界，人工复核加标** | ✅ 采纳 | 人体工学类依据公开设计规范；工程类只给提问清单 |
| D17 | **目标用户含“已请装修方/设计师，但亲自选家具定布局的屋主”** | ✅ 采纳（2026-11 修订） | 解决“设计模板怎么用”与“发给家人/设计师确认”的真实场景 |

### 被明确否决的方案

| 方案 | 否决原因 |
|---|---|
| 师傅入驻平台 | 供给侧没有动机，履约风险高 |
| 纯 2D 平面线框 | 屋主缺乏空间体量感，高度维度表达弱，传播力差 |
| 抓取贝壳/链家/安居客户型图 | 已有高额不正当竞争判例，法律风险极高 |
| 照片生成 2D/3D 户型 | 无比例尺与透视畸变，产不出可靠尺寸 |
| 硬装拆改 / 承重墙判断 / 施工参数指导 | 超出软装工具边界，安全与法律责任不可控 |
| 小程序先行 | WebGL/Three.js 适配受限，且提审拖慢体验迭代 |

## 4. 工程与质量标准

- **AI 协同高质量交付**：不以“省工期”为由做降级妥协，架构分层、3D 质感、手机/桌面交互细节、自动化测试一步到位。
- **业务核心绝对纯净**：`@fitly/layout-engine` 与 `@fitly/content` 保持零 DOM/WebGL 依赖的纯 TypeScript 实现，便于未来扩展到任何端。
- **全流程可验证**：核心几何计算与每条避坑规则配备完整 Vitest 单测；端到端主流程配备 Playwright 验证。

## 5. 词汇表

| 词 | 含义 |
|---|---|
| **户型 / `Plan`** | 一套房子的平面与层高结构：多房间边界、墙体、门窗、固定点位 |
| **试摆** | 在 3D 空间里放置/拖动家具，更换尺寸与外观材质，实时看净空与遮挡 |
| **净空 / 间距** | 两个物体之间可通行的距离（含方向性，如“衣柜正前方”），单位统一 `mm` |
| **辅助描墙与校准** | 上传 2D 户型底图后，辅助提取墙线轮廓并标定一段已知墙长换算真实比例 |
| **触发器** | 决定某条避坑提示“什么时候出现”的条件 |
| **快照 / 对比** | 云端/本地保存的方案版本，支持任意两版同场景或分屏对比 |
| **blocking / costly / annoying** | 坑的严重度分级，决定提示强度 |
